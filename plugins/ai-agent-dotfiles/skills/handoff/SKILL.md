# 세션 핸드오프

이 세션에서 한 일을 기록하고, 남은 일을 이슈로 옮겨 다음 세션이 이어받게 한다.

**핵심 제약: 파일 하나를 계속 키우지 않는다.** 기존 워크로그에 덧붙이지 말고 새 파일을
만든다. 이미 쓰인 기록은 완결된 것이고, 뒤에 덧붙이면 "언제까지가 그때의 판단이었나"가
사라진다.

## 절차

### 1. 상태 확인

```bash
git log --oneline -15
git status --short
ls docs/worklog/pending/ 2>/dev/null
gh issue list --state open 2>/dev/null   # 이슈를 쓰는 저장소라면
```

`docs/worklog/{pending,completed}/` 가 없으면 만든다. 저장소가 다른 자리를 쓰고 있으면
(`notes/`, `HANDOFF.md` 등) 그쪽을 따른다 — 이 스킬은 자리를 강요하지 않는다.

### 2. 워크로그 작성

`docs/worklog/pending/YYYY-MM-DD-<슬러그>.md` 를 **새로** 만든다. 슬러그는 영문
kebab-case 이고 이 세션이 다룬 일을 가리킨다 (`window-name-split` 처럼).

같은 날 같은 주제가 이미 있어도 **덧붙이지 않는다.** `-2` 를 붙이거나 더 구체적인
슬러그를 쓴다.

```markdown
# YYYY-MM-DD <주제>

**브랜치**: <branch> | **커밋**: <해시 범위> | **이슈**: #<번호>

## 한 일
- 결과까지 포함해서. 코드로 알 수 있는 것은 빼고.

## 결정
- 결정 + 근거. 나중에 뒤집으려면 왜 그랬는지가 필요하다.

## 막힌 것
- 재현 방법, 에러, 우회책. 없으면 이 절을 지운다.

## 다음
- [ ] 구체적인 다음 스텝. 이슈로 옮긴 것은 번호만 적는다.
```

**적지 말 것** — 계획 문서에 이미 있는 내용. 경로와 항목 번호로 가리키기만 한다.

### 3. 끝난 일을 옮긴다

`pending/` 의 항목 중 이 세션에 끝난 것이 있으면 옮긴다. 내용은 고치지 않는다.

```bash
git mv docs/worklog/pending/<파일> docs/worklog/completed/
```

### 4. 이슈 갱신 (이슈를 쓰는 저장소만)

워크로드는 워크로그가 아니라 이슈에 있다. 워크로그는 "무슨 일이 있었나", 이슈는
"무엇이 남았나"다.

```bash
gh issue create  --title "<한 줄>" --body "<맥락 + 관련 계획 문서 경로>"
gh issue comment <번호> --body "<무엇이 끝났고 무엇이 남았는지>"
gh issue close   <번호> --comment "<완료 근거: 커밋 해시, 테스트 결과>"
```

이슈 본문에는 **계획 문서 경로와 항목 번호**를 적는다. 계획을 복사해 넣지 않는다.

### 5. 커밋

```bash
git add docs/worklog
git commit -m "docs(worklog): <주제>"
```

**push 와 이슈 생성·종료는 사용자 확인을 받고 한다.** 둘 다 저장소 밖에 보이는
행위다. 무엇을 만들지 먼저 보여주고 승인을 받는다.

## 멈춰야 하는 신호

| 내가 하고 있는 것 | 무엇이 틀렸나 |
|---|---|
| 기존 워크로그 파일 끝에 이어 씀 | 완결된 기록을 고치고 있다. 새 파일을 만든다 |
| diff 로 알 수 있는 변경 목록을 나열함 | 코드가 이미 말하는 것이다. 왜 그렇게 했는지를 적는다 |
| 계획 문서 내용을 복사해 넣음 | 두 벌이 되면 곧 어긋난다. 경로로 가리킨다 |
| 성공한 것만 적음 | 폐기한 시도가 다음 사람의 시간을 가장 많이 아낀다 |
| 확인 없이 push 하거나 이슈를 만듦 | 저장소 밖에 보이는 행위다. 먼저 물어본다 |
| "다음"에 "리팩터링 계속" 같은 걸 적음 | 다음 사람이 그대로 실행할 수 없으면 다음 스텝이 아니다 |

## 원칙

- 대화에서 실제로 확인된 사실만 적는다. 추측은 `추측:` 으로 표시한다.
- 실패와 폐기한 시도도 적는다.
- 이어받는 쪽은 `pending/` 만 읽으면 되도록 쓴다. `completed/` 를 읽어야 이해되는
  워크로그는 잘못 쓴 것이다.

## 이 스킬이 여기 있는 이유 (2026-08-29)

같은 내용이 세 저장소에 복붙돼 있었다 — 두 벌은 md5 가 같았고 한 벌만 이슈 연동까지
확장돼 있었다. 고치면 세 군데를 고쳐야 하고, 실제로는 한 군데만 고쳐져 갈라져 있었다.

**세 번 복사한 것은 프로젝트 지식이 아니라 절차 지식이다.** 프로젝트 스킬은 그 코드와
수명이 같아야 하는데(`docs/skills.md`) 이건 어느 저장소에서 꺼내도 말이 됐다. 그래서
플러그인으로 올려 한 벌만 남긴다. 확장판을 기준으로 삼고, 그 저장소에만 있던 자리
(`docs/worklog/README.md` 참조, 특정 계획 문서 경로)는 걷어냈다.
