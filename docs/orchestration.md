# 오케스트레이션 — 서브에이전트를 언제 묶어 띄우나

`docs/subagents.md` 가 "어떻게 정의하고 부르는가" 라면, 이 문서는 **"실제로는 안 하고 있었다"** 를
숫자로 확인하고 그 습관을 바꾸기 위한 규칙이다. 2026-08-30 기준.

## 먼저 센다

세션 기록 873개 · 프롬프트 2825개에서 `Agent` 도구 호출을 셌다.

| | |
|---|---|
| 서브에이전트 호출 총계 | **422회** (28개 세션) |
| 한 응답에 1개만 띄운 경우 | **416회** |
| 2개 이상 동시에 띄운 경우 | **1회** — 0.2% |
| 사람 개입 없이 줄줄이 나간 구간 | **88개**, 합쳐서 왕복 **226번** |
| 그중 최악 | 13연속 1번, 9연속 3번, `general-purpose` 8연속 1번 |

유일하게 병렬로 띄운 1회는 이것이었다.

```
Explore × 6 동시   "Rebuild answer key Q01-Q05" … "Q26-Q30"
```

그리고 가장 긴 순차 구간 13개는 이것이었다.

```
 1-3.  Verify T3 batch 0 / 1 / 2
 4-5.  Verify T0 batch 0 / 1
 6-7.  Verify T2 batch 0 / 1
 8.    Verify T1 drafts (both batches)
 9-13. Draft T1v3 batch 0 / 1 / 2 / 3 / 4
```

**같은 모양이다.** 위는 6개를 한 번에 보냈고 아래는 13개를 한 개씩 보냈다. 아래도
왕복 2번(검증 8개 + 초안 5개)이면 끝날 일이었다. 배치 번호가 붙어 있다는 것 자체가
"서로의 결과가 필요 없다" 는 증거인데도 그렇게 갔다.

**위임을 안 한 게 아니다. 422번 했다. 묶지 않았을 뿐이다.**

`docs/subagents.md` 에 "서로의 결과가 필요 없으면 한꺼번에 띄운다" 를 적어두고 그걸 위해
`inspector` 까지 만들어 두었는데, 호출 집계에서 `inspector` 는 0회였다. 규칙과 도구를 만들어
놓고 실행이 안 되는 상태가 두 달 갔다.

## 왜 순차가 되나

병렬은 **한 응답 안에 `Agent` 블록이 여러 개 나가야** 성립한다. 순차로 굳는 이유는 셋이다.

1. **할 일을 하나씩 발견한다.** 하나 띄우고 결과를 보고 다음을 정하면 구조상 영원히 순차다.
   묶으려면 띄우기 *전에* 목록이 손에 있어야 한다.
2. **캐치올로 샌다.** 위임 422회 중 `general-purpose` 가 230회다. 전문 에이전트 19개 중
   12개는 한 번도 안 불렸다.
3. **워크플로 뒤에 숨는다.** `/autopilot` 31회. 편하지만 무엇이 몇 개 떴는지 안 보인다.

## `/autopilot` 안에서 실제로 무슨 일이 일어나나

31번 쓴 것치고 안이 안 보이므로 `skill-bodies/autopilot/SKILL.md` 를 읽고 정리했다.
(`skills/<이름>/SKILL.md` 는 shim 이고 본문은 `skill-bodies/` 에 있다 — OMC 스킬을
읽을 때 이걸 모르면 껍데기만 보게 된다.)

| Phase | 하는 일 | 띄우는 에이전트 |
|---|---|---|
| 0 확장 | 아이디어 → 스펙 (`.omc/autopilot/spec.md`) | analyst + architect |
| 1 계획 | 스펙 → 구현계획 (`.omc/plans/`) | architect + critic |
| 2 실행 | 계획 실행 | executor **(독립 단위는 병렬)** |
| 3 QA | build/lint/test 반복, 최대 5회 | 이름 붙은 것 없음 |
| 4 검증 | 다관점 리뷰 | architect + security-reviewer + code-reviewer **3개 병렬** |
| 5 정리 | 상태파일 삭제 + cancel | 없음 |

멈춤 조건도 파일에 있다 — 같은 QA 에러 3회 반복이면 정지, 검증 3라운드 실패면 정지,
입력이 vague 하면 `/deep-interview` 리다이렉트 제안. `pauseAfterExpansion` ·
`pauseAfterPlanning` 옵션이 있고 **기본값은 둘 다 `false`** 라서 중간에 안 멈춘다.

**그런데 Phase 2 와 4 는 "병렬" 이라고 적혀 있는데 로그에는 그 흔적이 없다.**
autopilot 을 31번 돌리는 동안 3개 동시 디스패치는 한 번도 없었다. 스킬 본문이
"parallel" 이라고 써 둬도, 실제로 한 응답에 여러 블록을 내보내는 것은 결국 메인 루프의
판단이다. **워크플로를 부른다고 병렬이 보장되지 않는다.**

## 전문 에이전트가 안 불리는 이유

위임 422회 중 230회가 `general-purpose` 였다. 안 불리는 12개의 `description` 을 읽어보면
이유가 보인다.

```
analyst            "Pre-planning consultant for requirements analysis (Opus)"
security-reviewer  "Security vulnerability detection specialist (OWASP Top 10 …)"
verifier           "Verification strategy, evidence-based completion checks …"
```

**12개 전부가 "무엇인지" 로 시작하고 "언제 쓰는지" 로 시작하는 것은 하나도 없다.**
`docs/skills.md` 에서 직접 낸 결론 — *"안 걸리는 것은 대개 description 이 틀린 것"* —
이 OMC 자신의 에이전트 카탈로그에도 그대로 적용된다.

이건 남의 플러그인이라 고칠 수 없다. 그래서 대응은 하나뿐이다 — **이름을 직접 지정한다.**
(본문에는 12개 전부 `Output_Format` 이 정의돼 있어서, 이름만 지정하면 형식은 나온다.)

## v5 의 뼈대

`plan → execute → review → verify` 가 정식 워크플로이고, 나머지는 대부분 여기로 route 된다.

```
autopilot · ralph · ultragoal        →  execute
deep-dive · sciomc · autoresearch    →  research   (앞의 셋은 5.0.0 에서 삭제됨)
merge-readiness                      →  review     (삭제됨)
```

`graph` 만 성격이 다르다. 대화형 스킬이 아니라 `omc graph run <descriptor.json>` CLI 러너이고,
DAG · journal 기반 재개 · `fan_out`/`join`/`concurrency_limit` 를 descriptor 로 선언한다.
descriptor 안의 `"kind": "agent"` 노드는 읽기 전용(Read/Glob/Grep)이다.
**병렬을 매번 말로 지시하는 대신 파일로 고정하고 싶을 때 볼 것.**

## 왜 "자꾸 idle 되고 비효율적" 으로 느껴지나

`Agent` 도구의 결과를 열어보면 이렇게 돼 있다.

```
"Spawned successfully"  /  "Async agent launched successfully"
```

**서브에이전트는 비동기다.** 띄우면 즉시 리턴하고, 실제 작업은 백그라운드에서 돈다.
결과는 나중에 알림으로 온다. 그래서 로그의 "에이전트 소요시간" 은 작업 시간이 아니라
*띄우는* 시간이다 (중앙값 2.8초, 98%가 10초 미만 — 이 숫자로 성능을 판단하면 안 된다).

여기서 체감 비효율이 나온다.

```
띄운다 → 할 일이 없다 → 턴이 끝난다 → idle → 알림이 온다 → 다시 띄운다 → idle → …
```

**순차로 N개를 띄우면 idle 도 N번이다.** 앞의 13연속 구간은 13번 멈췄다 갔다는 뜻이다.
묶으면 이 대기가 **1번**으로 접힌다. 토큰이나 왕복 수보다 이게 체감의 본체다.

두 번째 원인은 **에이전트가 끝나고도 보고를 안 하는 것**이다. 이 문서를 쓰는 세션에서
5개 중 1개가 완료 상태로 앉아만 있었고, `SendMessage` 로 결과를 따로 요청해야 했다.
띄운 개수와 받은 개수를 세고, 안 온 것은 **먼저 찔러야 한다.**

한편 오케스트레이션이 승인 때문에 막히는 일은 거의 없다 — 428회 중 classifier 차단은
1회(0.2%)였다. (차단은 대부분 `Bash` 19회로, 다른 종류의 마찰이다.)

## 언제 묶나

병렬은 공짜가 아니다. 6개를 띄우면 토큰도 6배다. 판단 기준은 하나뿐이다 —
**서로의 결과가 필요한가.**

| 상황 | 판단 |
|---|---|
| 읽기만 하고 대상이 안 겹침 (조사·리뷰·감사·수집) | **묶는다.** 위 226번 왕복이 전부 여기였다 |
| 같은 파일을 고침 | 순차. 충돌한다 |
| 앞의 결과를 봐야 다음이 정해짐 | 순차. 이건 진짜 의존이다 |
| 대상이 3개 미만 | 직접 한다. 띄우는 비용이 더 크다 |
| 대상이 10개 이상 | 묶되 쪼갠다. 한 에이전트가 여러 개를 맡는다 |

## 어떻게 부르나

세 가지가 다 있어야 걸린다 — **동시에 · 대상 열거 · 취합 방법.**

```
안 걸림   이 세 파일 문제 없나 봐줘
          → 하나씩 3번 나간다

걸림      inspector 로 a.ts b.ts c.ts 를 동시에 붙여.
          각자 사실만 보고하고, 다 오면 공통 문제만 뽑아줘
```

대상이 균일하면 범위로 쪼갠다 (위 `Q01-Q05 … Q26-Q30` 이 그 형태다).

```
Explore 6개를 동시에. 1번은 Q01-Q05, 2번은 Q06-Q10, … 6번은 Q26-Q30.
각자 근거 파일 경로와 함께 답만 돌려줘
```

## 에이전트를 이름으로 고른다

캐치올(`general-purpose`)로 보내면 무엇이 잘못됐을 때 어느 프롬프트를 고칠지 알 수 없다.

| 할 일 | 부를 것 |
|---|---|
| 사실 수집 (고치지 않음) | `ai-agent-dotfiles:inspector` — 대상 하나씩 붙여 병렬로 |
| 넓은 탐색 (어디 있는지 모를 때) | `Explore` (Claude Code 기본) |
| 코드 구현 | `oh-my-claudecode:executor` |
| 결함 찾기 | `oh-my-claudecode:code-reviewer` |
| 이 대화 맥락이 그대로 필요할 때 | `fork` |

좋은 병렬 대상의 조건은 `docs/subagents.md` 의 "좋은 에이전트의 조건" 과 같다 —
범위가 하나, 출력 형식이 정해짐, 결론을 내리지 않음. **결론은 다 모아서 호출자가 낸다.**

## 멈춰야 하는 신호

| 내가 하고 있는 것 | 무엇이 틀렸나 |
|---|---|
| 에이전트를 띄우고 결과를 본 뒤 또 하나 띄움 | 목록을 먼저 만들었어야 한다. 지금 남은 것을 한꺼번에 띄운다 |
| 대상 2개를 굳이 에이전트로 나눔 | 직접 하는 게 빠르다 |
| 같은 파일을 두 에이전트가 고침 | 충돌한다. 순차로 돌린다 |
| `general-purpose` 로 보냄 | 무엇이 잘못됐는지 나중에 못 고친다. 이름을 지정한다 |
| 워크플로 하나로 끝냄 (`/autopilot`) | 몇 개가 떴는지 안 보인다. 한 번은 단계별로 직접 불러본다 |

## 이 문서가 생긴 이유 (2026-08-30)

OMC 를 4.15.10 에서 5.0.2 로 올리면서 "무엇을 실제로 쓰고 있나" 를 셌다. 슬래시 477회 중
OMC 는 73회, 그중 `autopilot` 이 31회였다. 매직 키워드 훅은 전 세션 통틀어 2회 걸렸고,
MCP 도구 ~50개의 총 호출은 4회였다.

처음에는 "오케스트레이션 층을 안 쓰고 있다" 로 읽었는데, `Agent` 호출을 세어 보니 422회로
많았다. **빠진 것은 위임이 아니라 동시성이었다.** 그래서 규칙을 스킬이나 CLAUDE.md 가 아니라
이 저장소에 적는다 — `~/.claude/CLAUDE.md` 는 `omc setup` 이 덮어쓴다 (`README.md` 의
"저장소에 없는 것").
