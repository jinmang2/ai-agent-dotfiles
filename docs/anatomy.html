§1한 벌과 설치 위치

실체는 저장소에 한 벌. 나머지는 전부 심링크다. 그래서 설치 위치에서 고쳐도 곧바로 저장소의 변경으로 잡힌다.

같은 파일을 여러 번 복사하지 않습니다. 설치란 저장소의 파일을 각 도구가 찾는 자리에 링크로 걸어두는 일이고, install.sh 가 하는 게 정확히 그것입니다. 몇 번 돌려도 결과가 같고(멱등), 그 자리에 실제 파일이 있으면 지우지 않고 .pre-install-<타임스탬프> 로 옮겨둔 뒤 링크합니다.

눈여겨볼 지점은 공용 항목이 ~/.claude/ 밖에 있다는 것입니다. 창 이름 스크립트 하나를 Claude Code 와 Codex 가 같이 쓰기 때문에, 어느 한 도구의 설정 디렉토리에 두면 다른 도구가 남의 집을 참조하게 됩니다. 그래서 도구 무관한 것은 ~/.local/bin 과 ~/.config 로 갔습니다.

핵심 판단 — ~/.claude 자체에는 git 리모트를 걸지 않습니다. 자격증명과 대화 기록 전문이 같은 디렉토리에 살기 때문에, 화이트리스트 .gitignore 규칙 하나만 어긋나도 그대로 유출됩니다. 별도 디렉토리에 실체를 두면 그 위험이 구조적으로 사라집니다 — 실수할 여지 자체가 없어집니다.

세 개의 서랍

설정을 셋 중 하나로 분류합니다. 헷갈리면 “새 머신에서 이 값이 그대로 맞나?” 를 묻습니다.

서랍두는 곳예
공개해도 되는 공용 메커니즘이 저장소훅, window-label.sh, tmux, 공용 권한 규칙
머신 고유 값local/hosts/<호스트>/ — 비공개 서브모듈절대경로가 든 권한, tailnet 별칭
재설치로 복원되는 것아무 데도 안 둔다플러그인 본체, skills, OMC 생성물

이 저장소가 작은 이유가 세 번째 줄입니다. 프레임워크는 계속 쓰되, 재설치로 복원되는 것과 내가 만든 것을 섞지 않습니다.

§2settings.json

148행. 훅 9개, 플러그인 6개, 권한 18줄, 스테이터스라인 1개. 경로 하드코딩 0곳.

이식성 — "$HOME"

처음엔 홈 절대경로가 여덟 곳에 박혀 있었습니다. 다른 머신에 그대로 가져가면 훅이 전부 죽는 상태였습니다. 훅 커맨드가 셸을 거쳐 실행되는지 실제로 프로브를 걸어 확인한 결과 $HOME 이 확장됩니다. 그래서 설치 시점 경로 치환(sed) 같은 장치 없이 전부 이렇게 바뀌었습니다.

# JSON 문자열 안이라 큰따옴표가 이스케이프됨 "command": "\"$HOME\"/.local/bin/agent-window-label ⏳ busy"

스테이터스라인만 예외적으로 ${CLAUDE_CONFIG_DIR:-$HOME/.claude} 를 씁니다 — 계정마다 다른 HUD 캐시를 읽어야 하기 때문입니다.

설정 파일이 하나뿐이라는 제약

Claude Code 가 읽는 user 스코프 설정 파일은 ~/.claude/settings.json 하나뿐입니다. ~/.claude/settings.local.json 은 만들어도 조용히 무시됩니다 — .local.json 은 프로젝트 스코프에만 존재합니다. 그래서 “공용은 저장소, 이 머신만은 로컬 파일” 식으로 파일을 나눌 수가 없습니다.

대신 설치 시점에 합칩니다.

claude/settings.json 공용 (이 저장소) + local/hosts/<호스트>/settings-overlay.json 이 머신만 (비공개) = ~/.claude/settings.json 병합 생성물

오버레이가 없는 머신에서는 그냥 심링크입니다. 있으면 scripts/merge-settings.py 가 합친 실제 파일이 됩니다 — 병합 규칙에는 테스트 28개가 붙어 있습니다.

이 머신은 지금 후자입니다. ~/.claude/settings.json 은 심링크가 아니라 6,922바이트짜리 실제 파일입니다. 즉 생성물이므로 거기서 직접 고치면 다음 ./install.sh 에 덮어쓰입니다. 공용이면 claude/settings.json, 이 머신만이면 오버레이를 고칩니다. Claude Code 가 “Yes, and don’t ask again” 으로 거기에 직접 쓰는 일도 있어서, --check 와 설치 시점에 무엇이 사라지는지 diff 로 먼저 보여줍니다.

심링크는 쓰기를 통과시킵니다. 오버레이가 없어 심링크인 머신에서는, Claude Code 나 omc setup 이 ~/.claude/settings.json 에 써도 링크가 끊기지 않고 저장소 파일이 직접 고쳐집니다. Node 가 심링크를 따라 쓰기 때문입니다. model 이 세션 도중 opus → opus[1m] 로 바뀐 것이 저장소까지 그대로 반영된 것으로 확인했습니다. 다만 모든 쓰기 경로가 그런 것은 아닙니다 — §9.

§3훅 9개

상태 세 개와, 그 사이를 옮기는 이벤트 네 개. 그리고 “질문에 답했다” 는 이벤트가 없다는 사실을 우회하는 법.

  • » busy 작업중
  • ? waiting 입력대기
  • ✓ done 완료

상태는 tmux 윈도우 옵션 @cc 에 저장됩니다. 상태줄의 기호는 그 값을 보여주는 것뿐이고, 진실은 @cc 에 있습니다. 스크립트가 조기 탈출을 판단할 때도, 셸이 청소할 때도 이 값을 봅니다.

입력대기가 안 풀리던 문제

원래 설정에는 Notification(입력대기)은 있는데 그걸 되돌리는 이벤트가 없었습니다. 권한 프롬프트에 답해도 창은 그 턴이 끝날 때까지 물음표로 남아 있었습니다.

Claude Code 에는 “질문에 답했다” 는 훅 이벤트가 존재하지 않습니다. 대신 답변 직후엔 반드시 도구가 실행된다는 점을 이용했습니다 — PostToolUse 를 “작업 재개” 신호로 쓰면 됩니다.

가드 훅과 gstack 훅 3개만 동기입니다 — 이들은 종료코드 2 나 permissionDecision 으로 Claude Code 의 진행을 실제로 통제하므로 결과를 기다려야 합니다. 창 이름 훅 5개는 순수 표시이므로 전부 async: true 이고 턴을 막지 않습니다.

도구 실패도 PostToolUseFailure 로 똑같이 busy 로 되돌립니다. 도구가 실패해도 작업은 계속되기 때문입니다 — 실패했다고 창이 입력대기나 완료에 멈춰 있으면 그게 거짓말이 됩니다.

Codex 도 같은 스크립트를 부릅니다. 두 도구의 훅 JSON 형식이 같아서, ~/.codex/hooks.json 이 agent-window-label 을 그대로 호출합니다. 그래서 이 스크립트가 ~/.claude/ 밖에 있는 것입니다(§1).

§4이름과 상태를 가르다

예전엔 창 이름에 이모지를 박았다. 좁은 상태줄에서 이모지가 먼저 살아남고 정작 라벨이 3자로 잘렸다. 그래서 표시를 둘로 나눴다.

창 이름 하나에 세 가지를 욱여넣고 있었습니다 — 상태 이모지, 계정 마커, 라벨. tmux 상태줄은 폭이 정해져 있어서 이름을 잘라 보여주는데, 잘리는 쪽은 언제나 뒤, 즉 라벨입니다. 이모지 두 개는 표시 폭 4칸을 먹으면서 절대 잘리지 않았습니다. 정보량이 가장 큰 것이 가장 먼저 사라지는 구조였습니다.

고친 방식은 이름에서 정보를 빼는 것이었습니다. 이름은 라벨만 담고, 상태와 프로필은 창 옵션으로 남깁니다. 옵션은 폭을 먹지 않습니다. 그걸 상태줄 포맷이 읽어서 그립니다.

어디에무엇누가 쓰나
창 이름라벨만choose-tree 등 어디서든 이름은 이름이다
@cc상태 문자열 busy/waiting/done존재 자체가 “이 창에 에이전트가 있다”
@cc_sym1칸 기호 + 색상태줄
@cc_color창 번호에 입힐 프로필 색상태줄. 0칸짜리 마커다

이 옵션 이름 한 벌이 세 파일의 계약입니다 — agent/window-label.sh(쓴다), tmux/tmux.conf(그린다), shell/agents.sh(지운다). 한 곳만 고치면 조용히 어긋납니다.

칸 계산

어림짐작이 아니라 세어서 정했습니다. 폭 76 기준으로 세션명 5칸과 시계 7칸을 빼면 창 목록에 64칸이 남습니다. 창당 고정비는 4칸(양옆 공백 2 + 번호 1 + 기호 1)입니다.

dev 1»myrepo 2?client 3✓api-se 4 ai-agent-dotfiles 22:31 └세션 └번호색=프로필 └기호=상태 └라벨 6자 └활성 창은 17자

번호 배경색이 어느 도구·계정인지를 말합니다 — 33 claude, 135 claude-team, 208 codex. 기호는 상태입니다. 콜론을 뺀 것도 창당 1칸씩 벌기 위해서입니다.

결과적으로 같은 자리에서 라벨이 3자에서 6자로 늘었습니다. 비활성 창은 #{=6:window_name}, 지금 있는 창은 #{=17:window_name} 로 잘립니다 — 지금 있는 창은 이름을 온전히 알아야 하니까요.

setw -g automatic-rename off 가 없으면 tmux 가 실행 중인 프로세스 이름으로 창 이름을 계속 덮어씁니다. tmux 설정과 훅과 셸은 이 지점에서 결합돼 있습니다.

라벨 우선순위

순위출처결과 예
1@cc_label — 손수 고정한 작업명결제-마이그레이션
2git 저장소 루트 이름ai-agent-dotfiles

24자를 넘으면 … 로 자릅니다(AGENT_LABEL_MAXLEN). git 브랜치는 일부러 뺐습니다 — 수시로 바뀌어서 창을 식별하는 데 도움이 안 되고, worktree 를 쓰면 디렉토리 이름에 이미 브랜치가 반영됩니다.

cwd 를 어디서 읽는가

원래는 tmux 의 #{b:pane_current_path} 를 썼습니다. 그런데 그건 셸의 cwd 라서, Claude 세션이 다른 디렉토리로 옮겨가도 따라가지 않습니다. 지금은 훅이 stdin 으로 받는 JSON 에서 cwd 를 꺼내 씁니다 — 이게 세션의 실제 작업 디렉토리입니다.

# stdin JSON 에서 cwd 추출 (jq 없이 sed 로 — jq 미설치 환경 대비) cwd=$(printf '%s' "$payload" \ | sed -n 's/.*"cwd"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/p' | head -1)

JSON 이 비어 있으면 tmux 값으로, 그것도 없으면 $PWD 로 단계적으로 물러납니다. 어느 단계에서 실패해도 훅은 exit 0 입니다 — 창 이름 때문에 에이전트가 멈추면 안 됩니다.

작업명 고정

Claude Code 안에서 ! 접두사로 실행합니다 — 그래야 PWD 가 세션의 cwd 와 같습니다. 그 pane 에서 에이전트가 돌고 있으면 셸에 직접 입력할 수 없기도 합니다.

$ !ccname 결제-마이그레이션 결제-마이그레이션 $ !ccname --clear ai-agent-dotfiles ← 자동으로 복귀

작업명은 @cc_label 에 저장되므로 훅이 덮어쓰지 않습니다. 상태 기호와 색만 계속 바뀝니다.

§5주인이 둘이다

에이전트가 창을 떠났다는 이벤트는 없다. 그래서 “셸이 프롬프트를 그렸다” 를 그 신호로 쓴다.

§3의 상태 기계에는 빠져나가는 길이 없습니다. Stop 훅은 턴이 끝났을 때 불릴 뿐이고, 에이전트를 강제 종료하면 아무 훅도 불리지 않습니다. 예전엔 종료한 뒤에도 완료 표시가 그대로 굳어 있었습니다 — 창은 “다 됐다” 고 말하는데 실은 아무도 없는 상태입니다.

해결은 다른 쪽에서 나왔습니다. 셸 프롬프트는 그 창에 전경 프로그램이 없을 때만 그려집니다. 그건 정확히 “에이전트가 없다” 와 같은 뜻입니다. 그래서 PROMPT_COMMAND 에 정리 함수를 답니다.

이름 비교만으로는 부족합니다. 에이전트는 보통 이름을 라벨 그대로 둔 채 죽습니다. 그래서 “이름이 이미 맞으니 할 일 없다” 고 빠져나가면 완료 기호가 영원히 굳습니다. 셸 쪽은 이름이 맞더라도 @cc 가 남아 있으면 치웁니다.

탭 하나가 창 이름을 “done” 으로 바꾼 사고

셸 쪽은 tmux 값 세 개를 한 번에 읽습니다. 처음엔 탭으로 이어 붙여 read 로 쪼갰는데, 탭은 IFS 의 공백류라 read 가 연속된 탭을 하나로 합칩니다. @cc_label 이 빈 창에서는 필드가 하나 밀려서, @cc 의 값 done 이 “손수 고정한 작업명” 자리로 들어왔습니다. 창 이름이 done 이 됐습니다.

구분자를 US(0x1f) 같은 비인쇄 문자로 바꾸는 길도 막혀 있습니다 — tmux display -p 가 비인쇄 문자를 옥탈 이스케이프 넉 자로 바꿔 내보냅니다. 그래서 read 대신 파라미터 확장으로 직접 쪼갭니다.

# 빈 필드가 사라지지 않도록 read 를 쓰지 않는다 cur=${out%%$'\t'*}; out=${out#*$'\t'} manual=${out%%$'\t'*}; state=${out#*$'\t'}

git 호출은 디렉토리당 한 번만 돕니다(_CC_LABEL_CACHE). 프롬프트마다 git rev-parse 를 부르면 프롬프트가 느려집니다. SSH 로 다른 머신에 들어간 창은 원격 셸이라 로컬 tmux 이름을 못 바꿉니다 — 알려진 한계입니다.

§6프로필 색

agent/profiles.conf — 어느 도구의 어느 계정이 그 창을 쓰고 있는지를 0칸으로 말하는 법.

프로필은 도구 + 계정입니다. 창 번호의 배경색이 그걸 나타냅니다. 색은 자리를 차지하지 않으므로 라벨을 밀어내지 않습니다.

# <AGENT_PROFILE 값> <tmux 색> claude colour33 claude-team colour135 codex colour208 gemini colour41 copilot colour178 antigravity colour160

33 claude · 135 claude-team · 208 codex · 41 gemini · 178 copilot · 160 antigravity — 색을 - 로 두면 그 프로필만 번호에 색을 입히지 않습니다.

표시를 스크립트에 박아넣지 않고 표로 뺐습니다. “개인은 무표시” 방식은 계정이 셋이 되는 순간 무너지기 때문입니다 — 그때는 어느 계정이 무표시여야 할지 답이 없습니다. 표라면 줄만 추가하면 됩니다. 표에 없는 이름이 들어오면 색 없이 라벨만 나옵니다 — 실패하지 않고 조용히 물러납니다.

같은 것을 가리키는 두 변수

헷갈리기 쉬운 지점이라 적어둡니다. tmux 창 번호색과 HUD 의 profile: 표시는 서로 다른 변수를 봅니다.

무엇보는 값
tmux 창 번호색$AGENT_PROFILE → profiles.conf 조회
OMC HUD 의 profile:basename($CLAUDE_CONFIG_DIR) — AGENT_PROFILE 을 아예 모른다

어긋난 창이 실제로 나왔습니다. CLAUDE_CONFIG_DIR 만 걸린 채 실행된 세션이 team 계정을 쓰면서 창에는 개인 색을 달고 있었습니다. 그래서 AGENT_PROFILE 이 없으면 window-label.sh 가 CLAUDE_CONFIG_DIR 의 basename 에서 앞의 점을 떼어 유도합니다(.claude-team → claude-team). 두 곳이 늘 같은 답을 내도록 규칙을 하나로 맞춘 것입니다.

실행 함수가 하는 일

claude-team() { CLAUDE_CONFIG_DIR=~/.claude-team AGENT_PROFILE=claude-team command claude "$@"; } codex() { AGENT_PROFILE="${AGENT_PROFILE:-codex}" command codex "$@"; }

개인 계정도 같은 모양으로 감쌉니다. 값은 기본값과 같아서 동작은 달라지지 않지만, 기본값에 기대던 두 가지가 명시적으로 켜집니다 — 창 번호색과 HUD 의 profile: 줄. 안 걸면 개인 세션의 HUD 에는 그 줄이 통째로 빠져서, 창 색으로는 계정이 구분되는데 HUD 로는 알 수 없었습니다.

다만 덮어쓰지는 않습니다. 이미 걸려 있는 CLAUDE_CONFIG_DIR 을 개인 계정으로 되돌리면 방금 고친 불일치가 반대 방향으로 되살아납니다 — team 세션 안에서 !claude 를 부르는 경우가 그렇습니다.

Codex 를 감싼 이유는 다릅니다. Codex 에는 CLAUDE_CONFIG_DIR 같은 단서가 아예 없어서 프로필을 유도할 방법이 없습니다. 안 걸어주면 기본값 claude 로 떨어져 Codex 창이 개인 Claude 의 파랑을 답니다 — 도구를 구분하려고 만든 표시가 거짓말을 하게 됩니다.

§7다중 계정

shell/agents.sh — 로그인은 완전히 가르되 2.2G 는 나눠 쓰는 법. 그리고 무엇을 나눠 쓰면 안 되는지.

격리의 원리

Claude Code 는 CLAUDE_CONFIG_DIR 로 설정 루트를 통째로 바꿉니다. Linux 에서 자격증명은 그 루트 안의 .credentials.json 평문 파일이므로(keychain 이 아닙니다), 루트만 바꾸면 로그인이 완전히 분리됩니다.

공유의 원리

격리된 루트 안에서 무거운 것들을 ~/.claude 로 심링크합니다. 대상은 settings.json skills plugins hooks hud commands agents CLAUDE.md 여덟 항목이고, 존재하는 것만 링크됩니다.

그런데 통째로 공유하면 안 됩니다. plugins/ 를 통째로 심링크했더니 두 계정이 OMC 사용량 캐시 파일 하나를 나눠 쓰게 됐습니다. 마지막으로 렌더한 계정의 5시간·주간 한도가 양쪽 HUD 에 다 떴습니다. TTL 90초가 지나도 최대 15분까지 옛 값을 먼저 내주고 뒤에서 갱신하므로, 한참 동안 틀린 숫자가 굳어 있었습니다.

여기서 규칙 하나가 나왔습니다.

설정과 내려받은 덩어리는 공유하고, 돌면서 쌓이는 상태는 계정별로 둔다.

그래서 이 항목들은 통째가 아니라 자식 단위로 링크합니다. 아래는 링크하지 않고 빈 디렉토리만 만들어 두는 자식들입니다.

경로무엇
plugins/oh-my-claudecode/OMC 사용량 캐시 .usage-cache-*.json
hooks/.omc/OMC 훅 상태 (세션별 디렉터리)
hud/cache/스테이터스라인 렌더 캐시. 세션 id 로 갈리지만 계정은 안 가린다
plugins/installed_plugins.json
known_marketplaces.json · .last_inuse_sweep		공유하고 싶어도 못 한다. installPath 가 config-dir 절대경로다

마지막 줄은 링크를 걸어도 Claude Code 가 tmp+rename 으로 곧바로 실제 파일로 갈아버려서, 점검이 영원히 “끊김” 을 보고하게 됩니다. 갈라도 손해는 없습니다 — 실제 내용물인 cache/ 와 marketplaces/ 는 여전히 공유되고, 각 계정은 settings.json 을 보고 알아서 다시 채웁니다.

새 자식이 생기면 알려줍니다. 목록에 없는 자식을 처음 보면 처음봄 으로 출력합니다 — 상태인지 설정인지 사람이 판단해서 CLAUDE_ACCOUNT_LOCAL 또는 ..._SHARED_SEEN 에 넣습니다. 판단을 자동화하지 않고 물어보게 만든 자리입니다.

명령

실제로 나왔던 출력입니다. 이 회귀를 어떻게 잡고 고쳤는지는 §8 에 있습니다.

복구가 파괴적이지 않습니다. 심링크가 실제 파일로 바뀌어 있으면 지우지 않고 .detached-<타임스탬프> 로 옆에 치운 뒤 다시 링크합니다. 그 파일이 사용자가 편집한 내용일 수 있기 때문입니다.

계정을 늘리려면 shell/agents.sh 의 CLAUDE_ACCOUNT_DIRS_<이름> 한 줄이면 됩니다. claude-<이름> 실행 함수와 claude-accounts 목록은 자동으로 따라옵니다. tmux 에서 구분하려면 profiles.conf 에 한 줄 더합니다.

§9함정

알고 쓰면 문제가 아니고, 모르고 쓰면 조용히 어긋나는 것들.

심링크가 끊길 수 있다

설정을 원자적으로 쓰는 코드 경로(tmp 파일 생성 후 rename)를 만나면 심링크가 실제 파일로 바뀌고, 저장소 추적이 조용히 끊깁니다. ./install.sh --check 로 잡고 ./install.sh 로 복구합니다. 기존 내용은 .pre-install-<타임스탬프> 로 보존됩니다.

다만 §2에서 봤듯 model 변경은 링크를 통과해 저장소까지 반영됐습니다. 모든 쓰기 경로가 위험한 것은 아니라는 뜻이고, 그래서 정기적으로 --check 를 도는 편이 낫습니다.

오버레이가 있으면 ~/.claude/settings.json 은 생성물이다

거기서 직접 고치면 다음 설치에 덮어쓰입니다. 공용이면 claude/settings.json, 이 머신만이면 오버레이를 고칩니다. Claude Code 가 “Yes, and don’t ask again” 으로 거기에 직접 쓰는 경우가 있으므로, --check 와 설치 시점에 무엇이 사라지는지 diff 로 보여줍니다.

~/.claude/settings.local.json 은 읽히지 않는다

user 스코프엔 그런 파일이 없습니다. 만들어도 조용히 무시됩니다. 도구용 환경변수는 shell/agents.sh 에서 export 합니다.

셸 함수는 대화형 셸에서만 산다

.bashrc 는 비대화형이면 앞부분에서 return 합니다. 새 창을 열거나 source ~/.bashrc. 창 이름이 셸 쪽에서 갱신되지 않는 것도 같은 이유입니다.

alias 가 함수를 가린다

예전에 손으로 넣은 alias claude-team=... 이 남아 있으면 agents.sh 의 함수 대신 그게 잡힙니다. install.sh 가 찾아서 주석 처리합니다. 같은 맥락에서 .bashrc 의 # >>> ai-agent-dotfiles >>> 블록은 통째로 갈아끼워집니다 — 거기 직접 쓴 것은 다음 설치에 사라집니다.

gstack 이 없으면

AskUserQuestion 관련 훅 3개가 조용히 실패합니다. Claude Code 는 훅이 느리거나 오류일 때만 “Ran N hooks” 를 표시하므로, 조용한 성공과 조용한 실패를 구분하기 어렵습니다. 새 머신에서 질문 관련 동작이 이상하면 여기부터 봅니다. ./install.sh --check 가 이런 외부 참조를 세어 확인 필요 로 보여줍니다.

훅 설정 리로드

settings.json 을 바꿔도 실행 중인 세션이 즉시 반영하지 않을 수 있습니다. @cc 에 프로브 값을 심어 라이브 리로드를 확인한 적이 있지만, 안 되면 /hooks 를 한 번 열었다 닫으면 됩니다.

Codex 훅은 신뢰 승인이 필요하다

~/.codex/hooks.json 배열에 항목을 끼워넣으면 인덱스가 밀려 기존 훅의 신뢰가 깨질 수 있습니다. 절차는 codex/README.md.

ccname 은 셸에서 못 친다

해당 pane 에서 에이전트가 돌고 있으면 셸에 입력할 수 없습니다. Claude Code 안에서 !ccname 작업명 으로 실행합니다 — ! 접두사가 세션의 cwd 에서 셸 명령을 돌려줍니다.

긴 작업명은 잘린다

24자 제한이라 그보다 길면 … 로 잘립니다. 게다가 상태줄에서 비활성 창은 여기서 다시 6자로 잘립니다. 바꾸려면 agent/label-of.sh 의 AGENT_LABEL_MAXLEN 과 tmux/tmux.conf 의 #{=6:...} 두 곳입니다.
