# 스킬 — Claude Code · Codex

## 형식은 사실상 같다

```
<스킬이름>/
  SKILL.md          필수. frontmatter + 본문
  scripts/          선택. 실행 코드
  references/       선택. 참고 문서
  assets/           선택. 템플릿
```

```markdown
---
name: skill-name
description: 언제 이 스킬이 걸리는지. 모델은 이 문장만 먼저 읽고 선택한다.
---

본문. 선택된 뒤에야 로드된다 (progressive disclosure).
```

`description` 이 전부다. 본문이 아무리 좋아도 여기서 안 걸리면 안 불린다.
**무엇을 하는지가 아니라 언제 쓰는지**를 쓴다.

## 탐색 경로

| 도구 | 경로 |
|---|---|
| Claude Code | `<프로젝트>/.claude/skills/` → `~/.claude/skills/` → 플러그인 |
| Codex | `$CWD/.agents/skills` → `$REPO_ROOT/.agents/skills` → `$HOME/.agents/skills` → `/etc/codex/skills` |

**주의**: 두 경로가 동시에 쓰인다. 공식 경로인 `~/.agents/skills` 에는 에이전트
공통 스킬(`skills` CLI 가 `~/.agents/.skill-lock.json` 으로 관리)이 들어가고,
OMX 가 설치한 것은 `~/.codex/skills` 에 들어간다 — `config.toml` 의
`[[skills.config]]` 로 경로를 지정하기 때문으로 보인다.
스킬이 안 잡히면 두 곳을 다 본다.

`~/.agents/skills` 는 여러 에이전트(codex, gemini-cli, copilot, cursor, …)가
공유하는 자리라 도구를 늘릴수록 값어치가 커진다. 복원은 `.skill-lock.json` 의
`sourceUrl` 을 보고 다시 설치하면 된다. 잠금 파일에 없는 스킬은 손으로 넣은 것이므로
출처를 따로 적어두지 않으면 새 머신에서 복원할 수 없다.

## 프로젝트 스킬 vs 전역 스킬

| | 두는 곳 |
|---|---|
| 그 저장소에서만 의미 있음 (빌드 절차, 그 코드베이스의 함정) | 프로젝트 `.claude/skills/` |
| 어디서나 쓰는 절차 | `~/.claude/skills/` |

프로젝트 스킬은 **프로젝트 저장소에 커밋한다.** 이 dotfiles 저장소로 끌어오지 않는다.
같이 일하는 사람도 받아야 하고, 그 코드와 수명이 같기 때문이다.

## 무엇이 실제로 걸리나 — 직접 쓴 스킬 15개를 세어본 결과

2026-08-29 기준. 세션 기록 920개에서 `Skill` 호출을 세고, 직접 쓴 프로젝트 스킬
15개의 구조와 대조했다.

```
스킬                    언제형  멈춤표  유래기록   표    호출
real-scenario-first       O       O       O       23    11회
measurement-cycle         O       ·       ·        0     6회
나머지 13개              6/13     ·       ·      0~9     0회
```

**13개가 한 번도 안 걸렸다.** 그중 7개는 `description` 이 *무엇을 하는지*만 적혀 있다 —
아래 규약의 첫 줄을 어긴 것이다.

정직하게 말하면 **이 표로는 인과를 못 가린다.** 구조가 좋아서 자주 걸린 건지, 그
프로젝트를 많이 해서인지 n=1 로는 구분되지 않는다. 그래도 "안 걸리는 스킬은 대개
description 이 틀렸다"는 쪽은 13개 중 7개라는 숫자가 받쳐준다.

## 스킬을 쓸 때의 규약

1. **`description` 은 *언제* 를 쓴다.** 모델은 본문을 읽기 전에 이 한 줄만 보고 고른다.
   "PDF 를 OCR 한다"가 아니라 "스캔 PDF 에서 표를 뽑아야 할 때". 안 걸리는 스킬의
   대부분이 여기서 죽는다.

2. **멈춰야 하는 신호를 표로 적는다.** 절차만 있으면 모델은 절차를 따르면서도 틀린
   방향으로 간다. `| 내가 하고 있는 것 | 무엇이 틀렸나 |` 두 칸이면 된다.
   *"사용자가 '당연히 그렇겐 안 한다'고 함 → 즉시 멈추고 이 스킬을 처음부터 다시 실행"*
   같은 항목이 실제로 작동한다.

3. **이 스킬이 생긴 실패를 적는다.** 규칙만 있으면 왜 그런지 몰라 예외를 만들어낸다.
   구체적인 사고 하나를 날짜와 함께 적으면 규칙이 규칙으로 남는다.

4. **산문보다 표.** 조건-결과가 있는 것은 전부 표로 간다. 모델이 훑기 좋고 빠뜨린
   칸이 눈에 띈다.

5. **프로젝트 스킬은 프로젝트에 둔다.** 그 코드와 수명이 같다. 예외는 하나 —
   **같은 스킬을 세 번 복사했다면 그건 절차 지식이지 프로젝트 지식이 아니다.**
   플러그인으로 올린다 (`plugins/ai-agent-dotfiles/skills/`). `handoff` 가 그 사례다.

## 스킬 · 서브에이전트 · 슬래시 명령

| | 무엇 |
|---|---|
| 스킬 | 절차 지식. 모델이 필요할 때 자동으로 끌어씀 |
| 서브에이전트 | 격리된 실행 단위. 자기 컨텍스트를 가짐 |
| 슬래시 명령 | 사용자가 명시적으로 부르는 것. `~/.claude/commands/<이름>.md` |

같은 일을 셋 다로 만들 수 있다. 기준은 **누가 언제 부르는가**다.
모델이 알아서 → 스킬. 내가 직접 → 슬래시 명령. 격리해서 여러 개 → 서브에이전트.
